# Phase 6 — UI Design Contract

> Visual and interaction contract for the Dynamic Pick Valuation phase. Generated by gsd-ui-researcher. Extends Phase 3, Phase 4, and Phase 5 design contracts — all prior tokens and patterns are inherited.
>
> **Phase 6 is a pure engine upgrade.** No new routes or pages are introduced. All UI changes are in-place extensions to existing pick display surfaces established in Phase 5. New UI elements are: (1) a timing recommendation badge with one-line reasoning inline on every pick, and (2) a demand-adjusted value display alongside the existing pick value — both rendered within the existing `AssetChip` and pick list contexts.
>
> **Note on `shadcn_new_init_required: false`:** shadcn/ui was initialized in Phase 3. Phase 6 does not require a new init — it inherits the existing installation.

## Color

Inherited from Phase 3, Phase 4, and Phase 5 shadcn CSS variable tokens. No new token roles added.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `hsl(var(--background))` — shadcn default near-white/near-black | Page background |
| Secondary (30%) | `hsl(var(--card))` — shadcn card surface | Cards, panels, pick list containers |
| Accent (10%) | `hsl(var(--primary))` — shadcn default blue | Inherited usage from Phase 5; pick slot projected slot badge; demand-adjusted value text in trade evaluator |
| Destructive | `hsl(var(--destructive))` — shadcn default red | Not used in Phase 6 — no destructive actions |

**Timing recommendation badge colors (new Phase 6 semantic treatment):**

Three mutually exclusive states. Each pick shows exactly one.

| Timing State | Badge Background | Badge Text | When Applied |
|---|---|---|---|
| Sell now | `bg-amber-100 dark:bg-amber-950/30` | `text-amber-800 dark:text-amber-200` | Calendar near peak (Feb–Apr) with early slot pick, OR team trending down mid-season |
| Hold until rookie fever | `bg-blue-50 dark:bg-blue-950/20` | `text-blue-700 dark:text-blue-300` | Default — calendar in buy window (Sep–Jan), or conditions don't trigger sell now |
| Use on the clock | `bg-green-50 dark:bg-green-950/20` | `text-green-700 dark:text-green-300` | Draft in progress or imminent |

**Rationale for color choices:**
- Amber "sell now": matches the established amber callout pattern from Phase 5 (strategic distinction banner) — amber = "act on this"
- Blue "hold": neutral information state — distinct from amber (action needed) and green (immediate)
- Green "on the clock": immediate/active state — same green family as positive delta values in Phase 3 risers list

**Timing reasoning string color:** Always `text-muted-foreground` regardless of timing state — the badge carries the color signal; the reasoning string is informational prose.

**Demand-adjusted value vs. league-adjusted value display:**
- League-adjusted value: `text-foreground` — the neutral pick value for display
- Demand-adjusted value (shown in trade evaluator pick context): `text-primary` — accent color indicates this is the trade-relevant figure
- When both are shown, demand-adjusted value appears first (it is the trade evaluation input); league-adjusted appears secondary in `text-muted-foreground`

**Dark mode:** OS-default via `prefers-color-scheme` — same as Phases 3–5. No mode toggle in Phase 6.

## Component Inventory

Phase 6 introduces no new page-level components. The following describes in-place extensions to existing Phase 5 components.

### PickValueDisplay (extension to Phase 5 AssetChip)

**Affected component:** `AssetChip` (Phase 5) — the pick chip variant specifically.

**Current Phase 5 pick chip layout (unchanged):**
```
[pick identity text] [projected slot badge ~1.04]
```

**Phase 6 extended pick chip layout:**
```
[pick identity text] [projected slot badge ~1.04] [timing badge]
[timing reasoning string — one line, muted]
```

**Visual focal point:** The timing badge is the primary visual anchor of the extended pick chip in Phase 6 pick display contexts. It is the only colored element in the row and must appear rightmost in the first row, after the projected slot badge, so the eye lands on it last and reads it as the action signal. The timing reasoning string on the second row supports the badge — it never competes with it.

Layout specification:
1. First row: `flex items-center gap-2`
   - Pick identity text (Label, 12px/400, `text-muted-foreground italic`) — unchanged from Phase 5
   - Projected slot badge — `bg-primary/10 text-primary rounded px-1 py-1` (Label, 12px/400) — unchanged from Phase 5
   - Timing badge — `rounded px-2 py-1 text-xs font-medium` + state-specific color classes (see Color section) — NEW Phase 6 element
2. Second row: timing reasoning string (Label, 12px/400, `text-muted-foreground`) — NEW Phase 6 element
   - Renders on its own line below the first row — `mt-1`
   - Single line, no truncation — reasoning strings are short by contract (one-liner from engine)
   - Absent when timing state is "use on the clock" and no additional context is needed (reasoning is self-evident: "Draft in progress — use or trade immediately")

**AssetChip structural change:** The pick chip changes from a single-row `inline-flex` to a `flex flex-col gap-1` to accommodate the reasoning line. The chip background and border-radius are unchanged.

### PickValueSummaryRow (new element within EvaluationOutputPanel pick rows)

**Affected component:** Phase 5 `EvaluationOutputPanel` — specifically the pick chip rows within the trade input party columns.

**Context:** When picks appear in the trade evaluator, the timing rec and demand-adjusted value need to be visible at the point of evaluation, not just in the asset chip. This context shows more detail than the chip.

Layout (within the trade evaluator pick row):
```
[pick identity] [slot badge] [timing badge]
[league-adjusted: 68.2] [demand-adjusted: ~74.1 (to this manager)]
[timing reasoning string]
```

Specification:
1. First row: `flex items-center gap-2` — same gap as extended AssetChip above
   - Pick identity text (Label, 12px/400, `text-muted-foreground italic`)
   - Projected slot badge — `bg-primary/10 text-primary rounded px-1 py-1` (Label, 12px/400)
   - Timing badge — `rounded px-2 py-1 text-xs font-medium` + state-specific color classes (see Color section)
2. Value row: `flex items-center gap-3 mt-1`
   - "League value:" label (Label, 12px/400, `text-muted-foreground`) + value (Label, 12px/400, `text-foreground`)
   - "To [manager name]:" label (Label, 12px/400, `text-muted-foreground`) + demand-adjusted value (Label, 12px/400, `text-primary`)
   - "[manager name]" is populated from the counterparty column header — if no manager name is set, renders as "To counterparty:"
3. Third row: timing reasoning string (Label, 12px/400, `text-muted-foreground`) — `mt-1` — same as AssetChip extension

**This expanded layout applies only in the trade evaluator context** — in all other pick display contexts (league pick lists, asset chips outside the evaluator), use the compact two-row AssetChip layout.

### LeaguePickList (new element for league-level pick display)

**Affected surface:** Existing league drill-in view (Phase 3). Phase 6 upgrades the pick capital display to show dynamic values where picks appear.

**Current state:** Phase 3 league drill-in shows pick capital in a static list (the exact UI was left to executor discretion in Phase 3). Phase 6 requires that wherever picks are listed at the league level, each pick shows the dynamic value and timing recommendation.

Layout per pick row in the league pick list:
```
[Year + Round text]  [Owner name]  [Slot range]  [Timing badge]  [Value]
[Timing reasoning]
```

Specification:
1. Main row: `flex items-center justify-between gap-2 min-h-[44px]`
   - Pick identity (Body, 14px/400): "2026 1st" — year + round, no owner name here (owner is in the next column)
   - Owner name (Label, 12px/400, `text-muted-foreground`): e.g. "Mike's"
   - Slot range (Label, 12px/400, `text-muted-foreground`): e.g. "~1.03–1.05" — projected range, not a single value
   - Timing badge (Label, 12px/400): same badge spec as AssetChip extension above
   - Value (Label, 12px/400, `text-foreground`): league-adjusted value number, right-aligned
2. Second row: timing reasoning (Label, 12px/400, `text-muted-foreground`) — `mt-1 pl-0`

**Batch recompute note:** The league pick list fetches all pick values in a single batch call to `GET /picks/{league_id}`. The loading state shows skeleton rows matching the count of picks in the league. Do not make per-pick API calls.

## Interaction States

Every data region that fetches from the API implements all four states (inherited from Phase 3):

| State | Behavior |
|-------|----------|
| Loading | Replace content with matching-height `Skeleton` components; no spinner |
| Success | Render data |
| Empty | Render empty state copy (see Copywriting Contract) |
| Error | Render error state copy inline (no full-page error); TanStack Query retry handles refetch |

**Phase 6 pick value loading states:**

| Context | Loading Behavior |
|---------|-----------------|
| AssetChip in trade evaluator | Timing badge replaced with `Skeleton` `w-16 h-4 rounded`; reasoning line replaced with `Skeleton` `w-48 h-3` |
| League pick list | Each pick row replaced with `Skeleton` `h-11 w-full` × N (where N = pick count from prior render or a default of 4) |
| Demand-adjusted value in evaluator | Value text replaced with `Skeleton` `w-10 h-4 rounded` while PickEngine computes |

**Pick value recompute trigger:**
- Pick values recompute when standings change — not on every page load.
- If cached pick values exist in `pick_values` table (computed within the current session), display cached values immediately. Show a "Last computed: {relative time}" label (Label, 12px/400, `text-muted-foreground`) near the pick list header — not per-row.
- "Recompute Picks" affordance: `Button variant="ghost" size="sm"` labeled "Recompute Picks" — appears adjacent to the "Last computed" label. Triggers batch recompute for the league's picks.

## Implementation Notes for Executor

1. **Engine upgrade, not a page build:** Phase 6 adds no routes. The execution surface is: (a) extend the Phase 5 `AssetChip` pick variant, (b) extend the Phase 5 `EvaluationOutputPanel` pick row, (c) upgrade the Phase 3 league drill-in pick capital section. That is the full frontend scope.

2. **Two value fields — keep them separate:** `league_adjusted_value` and `demand_adjusted_value` are distinct fields returned by `GET /picks/{league_id}` and `GET /picks/{pick_id}/value`. Never merge or average them. `league_adjusted_value` is for league-level display (neutral). `demand_adjusted_value` is for trade evaluator display (personalized to the counterparty manager). The Phase 5 `TradeRepo.get_pick_value()` returns `demand_adjusted_value` — this is correct per Phase 6 integration design.

3. **AssetChip structural change is backward-compatible:** The chip changes from `inline-flex` to `flex flex-col`. Verify that all existing usages of `AssetChip` (player chips) are unaffected — the change applies only to the pick chip variant (`type === 'pick'` branch). Player chips remain single-row `inline-flex`.

4. **Timing badge is not a shadcn Badge:** The timing badge uses a custom `span` with Tailwind color classes (see Color section). Do not use shadcn `Badge` component for timing — its variant system does not map cleanly to the three-state amber/blue/green treatment. The existing shadcn `Badge` is still used for confidence bands (Phase 3) and position codes (Phase 5) — keep those usages unchanged.

5. **Batch fetch, not per-pick:** `GET /picks/{league_id}` returns all pick values for the league in one call. Cache using TanStack Query with a `staleTime` of 5 minutes (picks do not update on every page load). The "Last computed" timestamp comes from `computed_at` on the `PickValue` response — use the most recent `computed_at` across the batch to determine the display label.

6. **Future-year picks need visual distinction:** Picks 2+ years out have no current standings signal — they use a neutral slot and future discount. Append "(future year)" in `text-muted-foreground` after the pick identity text. Omit the slot range badge for future-year picks — the projected slot is not meaningful without standings data. Show only the discounted value and timing reasoning.

7. **Phase 5 pick value redirect:** The `TradeRepo.get_pick_value()` method is updated in Phase 6 to call `PickEngine.compute()` instead of the Phase 2 baseline. After this change, every pick shown in the Phase 5 trade evaluator automatically receives dynamic values. No frontend trade evaluator code changes are required for the value source change — the API response shape is unchanged (it still returns a float for the pick's trade value).

8. **Recompute Picks button placement:** The "Recompute Picks" button and "Last computed" label appear once per league pick list, in the section header row — not on individual pick rows. Layout: `flex items-center justify-between` section header row with "Pick Capital" heading (Heading, 18px/600) on the left and `[Last computed: X] [Recompute Picks]` on the right.

9. **Direction label fallback for demand factor:** If Phase 4 has not been run for a league (no manager profiles exist), pick demand factors default to neutral (0.5 per engine design). In this case, omit the "To {Manager}:" demand-adjusted row in the trade evaluator — show only the league-adjusted value. This avoids surfacing a "To counterparty: 68.2" value that is identical to the league-adjusted value and would create false precision.

10. **Class strength signal is always 0.0 in Phase 6:** The `class_strength_signal` field is present in the API response but should not be displayed anywhere in the UI in Phase 6. It is an internal engine input. Phase 7 will expose class strength information through the Rookie Board, not through pick value displays.
